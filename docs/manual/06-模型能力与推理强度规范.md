# 主流大模型上下文长度（Context Window）与推理强度（Reasoning Effort）规范白名单

> 本文档基于 [farion1231/cc-switch](https://github.com/farion1231/cc-switch) 的工程实践（包括其内置的 `model_capabilities.rs`、官方模板 `gpt5_5_template.json`、`codex_deepseek_catalog_template.json`、`codex_native_responses_template.json`）以及各大厂商官方 API 技术规范整理。
> 
> 本文档旨在作为 Tomo 网关导出模型能力、DSH（DeepSeek Harness）接入配置以及后续网关 UI 用户自定义能力配置的**官方基准与默认预设参考**。

## 二、cc-switch 项目中的关键设计原则借鉴

在分析 [farion1231/cc-switch](https://github.com/farion1231/cc-switch) 的工程实现（特别是在 `src-tauri/src/codex_config.rs` 和 `model_capabilities.rs` 中）后，可以提炼出三条对 Tomo 极其关键的设计准则：

1. **白名单必须精确，绝对不能依靠简单前缀模糊匹配**：
   * 在 cc-switch 中，纯文本模型（`CONFIRMED_TAILS`）采用的是**严格后缀完全匹配**，而不是 `contains("glm")`，因为 GLM 系列中带 `v` 后缀（如 `glm-5.2v`）的模型是具备多模态能力的。
   * 类似地，推理能力也严禁通过 `contains("gemini")` 批量赋予。例如，非思考类模型强行接收 `thinkingConfig` 会导致供应商 API 报错。

2. **多层级配置继承机制（用户覆盖优先，系统白名单作缺省）**：
   * **用户显式配置**（User Declared）：若用户在 UI 中对特定模型自定义了 `context_window` 或 `reasoning_levels`，则完全以用户配置为最高优先级生效。
   * **系统内置模板 / 白名单**（Official Preset）：若用户未配置，则回退到官方基准模板。
   * **安全保守底线**（Fail-safe Default）：对于完全未知的自定义模型，默认按纯文本或仅支持常规上下文（如 128k）处理，且不向 DSH/Codex 等下游声明虚假的推理能力。

3. **规范化档位映射（Canonical Efforts）**：
   * 下游客户端（如 Codex/DSH）使用的档位集合固定为标准枚举（如 `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`）。
   * 系统统一做过滤和排序（无论用户传入何种顺序，均按由低到高规范输出），对于目标协议不支持的档位做显式转译（如 OpenAI `reasoning_effort` 映射为 Google Cloud Code 的 `thinkingBudget` 整数 Token 预算：1024, 2048, 8192 等）。

## 三、Tomo 网关 UI 用户自定义能力设计方案

用户要求：**在 UI 中支持用户自行配置相关模型支持的推理强度（Reasoning Effort）与上下文长度（Context Window），并由系统提供合理的默认值。**

### 1. 数据模型与存储结构
在 `GatewaySettings.swift` 中为模型级配置扩展定义：

```swift
public struct GatewayModelCapabilityOverride: Codable, Equatable, Sendable {
    /// 目标模型 ID，例如 "google/gemini-3.8-flash-tiered" 或通配 "gemini-3.8-flash-tiered"
    public var modelID: String
    /// 自定义上下文窗口大小，为空时采用系统默认值
    public var contextWindow: Int?
    /// 自定义最大输出 Token 数，为空时采用系统默认值
    public var maxTokens: Int?
    /// 是否支持多模态图片输入
    public var supportsImage: Bool?
    /// 用户配置的可用推理强度列表，例如 ["off", "low", "medium", "high"]。若为空列表则视为不支持推理调节
    public var reasoningLevels: [String]?
    /// 默认推理强度
    public var defaultReasoningLevel: String?
}
```

在 `GatewaySettings` 中新增字段：
```swift
public var modelCapabilityOverrides: [String: GatewayModelCapabilityOverride] = [:]
```
持久化保存至 `gateway-settings.json`。

### 2. UI 交互设计
在网关设置界面的**模型管理 / 接入配置**板块中，点击任意模型右侧的「配置模型能力」按钮，弹出抽屉或模态窗口：
* **上下文长度（Context Window）输入框**：数字输入，附带常见快捷预设标签（如 128K、256K、1M）。
* **最大输出（Max Output Tokens）输入框**：数字输入，附带预设标签（如 4K、8K、16K、64K）。
* **图片多模态支持开关（Toggle）**：开启/关闭当前模型图片支持。
* **推理强度调整开关与选项集（Reasoning Levels）**：
  * 开关：开启后允许选择档位。
  * 勾选框组：`off`（关闭思考/默认）、`low`（轻度）、`medium`（平衡）、`high`（深度）、`xhigh`（极高）。
  * 默认档位下拉单选。
* **「恢复官方推荐默认值」按钮**：点击可直接载入上述 Markdown 表格中的官方推荐配置。

### 3. 网关到 DSH 的元数据导出联动
当用户保存自定义模型能力后，`DSHGatewayConfigurator` 和网关的 `/v1/models` 按以下逻辑合并生成：
1. **优先提取**：读取 `gateway-settings.json` 中用户的 `modelCapabilityOverrides[modelID]`。
2. **缺省填充**：若用户未针对该模型配置，则查阅上述标准基准表。
3. **安全兜底**：若该模型完全未知，则不声明 `reasoningEfforts`，模态保守声明为 `[text]`，上下文保守设为 `131072`。
4. **生成 `~/.dsh/settings.yaml`**：写入严谨真实的字段，避免虚标导致下游客户端报错。
