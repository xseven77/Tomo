# 通用开放 API 文档站调研与实施方案

日期：2026-09-18。状态：方案草稿，尚未实现 React 工程或桌面文档托管。

## 1. 目标与推荐方案

文档面向用户自行开发应用，产品定位是 Tomo 桌面端通用开放 API。支持 Web、原生移动端、其他桌面应用、CLI、自动化脚本和服务端接入；Web 插件只是可选的静态托管方式。文档站使用 React 不代表调用 API 的应用也必须使用 React。

在 Tomo 仓库的 `app/developer-docs` 新增 React 文档工程，正文使用 Markdown，推荐采用 **Docusaurus classic 文档主题 + 本地搜索**。构建为静态文件后随桌面应用分发，通过桌面内置 HTTP 服务的 `/developer/` 访问。运行桌面应用时无需 Node、Next.js 服务或互联网连接。

用户可以浏览 API、搜索当前或历史版本、查看版本差异摘要，并根据自己安装的桌面版本选择对应文档。第一阶段完成文档，第二阶段才开始工程与桌面代码。

正文以普通 `.md` 为主；仅交互组件使用 React / 必要的 MDX。文档站的框架版本和 API 文档版本分别管理。

## 2. 开源方案调研

| 方案 | 适用点 | 本项目需要补充的工作 | 判断 |
| --- | --- | --- | --- |
| Docusaurus classic | React 文档主题、Markdown、导航、内置文档版本快照与切换、静态发布 | 本地搜索集成、历史元数据页面、桌面资源托管 | 推荐，版本管理需求最契合 |
| Nextra docs theme | React / Next.js 文档主题，支持静态导出；官方文档提供 Pagefind 搜索集成说明 | 需要另行确定多版本目录、版本导航及历史发布规则 | 备选，适合更偏定制的文档 UI |
| Fumadocs UI | React 文档 UI 与可组合组件，可按产品风格定制 | 需要进一步验证选定应用框架的静态导出、版本管理和离线打包 | 备选，定制能力值得后续评估 |

Docusaurus 官方版本机制会保存正文和导航快照，后续编辑当前文档不影响历史版本；本文采用这个能力，不额外自己实现一套正文版本数据库。[官方版本文档](https://docusaurus.io/docs/versioning)

Nextra 支持静态导出，搜索需要按静态导出说明完成索引构建。[官方静态导出文档](https://nextra.site/docs/guide/static-exports) Fumadocs 提供文档 UI 组件，若选择它，需单独完成本项目的版本与打包验证。[官方 UI 文档](https://www.fumadocs.dev/docs/ui)

这里的推荐基于本项目的“React、Markdown、离线桌面托管、历史版本”要求，不声称其他框架不能实现历史浏览。开始工程时固定依赖版本和 lockfile，并核查对应版本及搜索依赖的许可证。

### 搜索选择

推荐先验证 Pagefind：扫描构建后的静态页面，生成本地索引，支持用过滤器区分文档版本。它是需要接入的搜索工具，不是 Docusaurus 原生自带的本地搜索。[Pagefind 过滤器文档](https://pagefind.app/docs/filtering/)

搜索默认限定当前选择的文档版本；提供“所有版本”选项。每个结果显示文档版本、章节标题与摘要。页面正文标记版本过滤信息，导航、重复页脚和生成的敏感调试内容不进入索引。

Docusaurus 官方也列出 Algolia 和社区本地搜索方案；本项目优先选择本地索引，因为仅在用户 Mac 上运行的文档不能依赖公开抓取或在线搜索服务。[官方搜索文档](https://docusaurus.io/docs/search)

工程阶段先测试“配对、工作时长、供应商代理、SSE、target_token”等中文、英文和代码字段搜索。若 Pagefind 的中文检索结果不满足要求，再对比社区本地搜索插件，保持其余架构不变。

## 3. 当前桌面服务的适配结论

当前 `MobileSyncServer` 已有监听器和静态 Web 插件托管能力，可以复用 HTTP 服务，但不能直接把新文档打包到 `mobile-web`：该目录会被插件安装替换，而且目前仅有一个插件槽位。

当前状态与拟新增能力：

| 项目 | 当前状态 | 实施阶段设计 |
| --- | --- | --- |
| 文档 HTTP 路由 | 无 | `/developer/` 独立路径 |
| 文档资源 | 无 | app bundle 的 `DeveloperDocs` 目录 |
| 插件首页 | `/`，来自 mobile-web | 保持现有插件入口，文档走独立资源 |
| 服务开关 | 依附 Mobile 同步设置 | 文档开关可独立请求共享监听器启动 |
| API 文档版本 | 无发布快照 | 发布目录、版本选择器与变更记录 |
| 搜索 | 无 | 随应用分发的本地静态索引 |

文档默认通过 `http://127.0.0.1:58350/developer/` 打开，实际端口读取桌面配置。共享监听器使用条件应设计为“Mobile 服务开启，或开发文档开启”；Mobile 关闭时不能因文档启动监听器就意外开放全部 `/api/v1/` API。需要在路由层保留 API 启用判断。

如果共享监听器同时面向局域网，静态文档也可能被局域网用户访问，不能把“浏览器打开 loopback 地址”当作“服务只允许本机访问”。如需仅本机文档，应增加远端访问限制或采用独立 loopback 监听器；这是工程阶段明确处理的访问策略。

公网映射后的文档访问是否开启由桌面设置控制，文档站不会主动上架到公网。静态文档只包含公开接口说明，不自动携带当前桌面 Token，也不调用 credentials。

## 5. 页面与开发体验

- 顶部：Tomo 开发文档、文档版本选择、搜索、浅色 / 深色切换。
- 左侧：快速开始、认证、API、各类客户端接入、多桌面服务、可选 Web 托管、常见问题。
- 正文：请求方法与路径、权限、参数、完整字段、响应示例、失败状态、兼容说明。
- 右侧：当前章节目录。
- 页头或页脚：文档版本、核验桌面版本、对应源码提交和最近修订时间。
- 版本历史页面：发布时间、对应桌面版本、变更摘要、迁移说明、进入历史文档的链接。

窄屏使用折叠导航和可横向滚动的字段表；代码块可复制。首期不做内嵌真实 API 执行器，示例使用占位符；后续如果做调试面板，Token 由用户手动提供且与搜索索引、静态资源隔离。

桌面设置增加“开发文档”区域：打开文档、复制本机地址、查看随应用附带的文档版本、控制文档访问。文档没有安装成功时显示明确提示，不能退回 Mobile 首页伪装成文档可用。

## 6. 版本管理与历史查询

### 三种版本独立管理

| 版本 | 示例 | 用途 |
| --- | --- | --- |
| 文档发布版本 | 拟从 `0.1.0` 开始 | 可浏览、可搜索的说明快照 |
| 桌面应用版本与提交 | `0.8.3 / build 100` + Git SHA | 确认实现基线 |
| snapshot schemaVersion | 当前 `1` | 快照结构标识，不覆盖全部路由能力 |

首版 `0.1.0` 目前只作为命名建议，尚未冻结或发布。首次正式发布必须记录其实际核验提交，不能继续沿用已变化的草稿基线。

同一个 snapshot schemaVersion 下已经可能存在新增接口，客户端不能据此判断某个 SSE 路由一定存在。文档发布元数据记录逐项能力与核验基线，不臆测各能力的最早桌面版本。

### 稳定地址设计

| 拟定路径 | 用途 |
| --- | --- |
| `/developer/` | 最新已发布版本的入口别名 |
| `/developer/0.1.0/.../` | 明确版本的稳定文档链接 |
| `/developer/next/.../` | 未发布正文，开发构建显示 |
| `/developer/history/` | 所有随当前应用分发的历史版本与变更摘要 |

需要显式配置最新版本也带版本路径，而不是完全沿用框架默认的最新版本无版本路径。版本切换尽量保留当前章节；目标版本没有对应章节时跳到该版本首页并提示。支持浏览器前进后退和直接打开历史章节。

“历史”首期包括发布版本的正文、导航、发布记录和跨版本搜索，不包含逐行 diff 界面，也不是历史 Agent 任务。逐次文字修订由 Git 保留；如需网页查询每次修订，应后续增加修订索引与差异视图，不能把 Git 仓库历史自动等同于网站已经支持所有修订查询。

### 发布元数据

每个文档版本记录：版本号、发布日期、状态、核验桌面版本/build、源码 SHA、文档源提交、功能能力列表、变更摘要和迁移说明。字段设计放在方案中，工程阶段再实现 releases.json 及校验器。

能力列表至少覆盖：snapshot、todayMinutes、直接 SSE、Agent SSE relay、供应商代理、宠物资源、凭证导出。最早支持版本如果没有核验，显示“未核验”，不能编造一个最低版本。

### 冻结与修订规则

1. 开放 API 或可选托管契约变更时，在同一个 PR 更新未发布正文和变更摘要。
2. 发布前按实际源码核验路由、字段和示例，确定文档版本及对应桌面提交。
3. 使用 Docusaurus 版本命令生成正文与导航快照，提交快照和元数据。未来工程中的命令示例是 `pnpm run docusaurus docs:version 0.1.0`，本阶段不执行。
4. 构建所有已纳入发布的版本和搜索索引，再一起打包桌面应用。
5. 历史版本原则上不改变接口语义；发现文案错误可修订并记录修订时间。语义变化发布新版本。

破坏性变化提高文档主版本并提供迁移说明；兼容新增能力提高次版本；纯说明纠错提高修订版本。文档版本号不会自动变更现有 API 路径。

不能把当前正文复制若干份当作过去版本。补录旧版文档时，应逐个检查旧 Git tag / commit 与相关接口测试；无法可靠还原的版本只列发布记录并标注“未提供 API 文档”。

首期将从首版开始的全部历史快照随桌面分发，实现离线查询。旧桌面应用只能看到构建时附带的版本，不会自动拥有未来文档；若以后提供在线最新版，需要额外设计更新校验和离线回退。

## 7. 静态构建与桌面打包

Docusaurus 可以生成静态站点；本项目仅在开发或发布机器使用 Node 工具链，桌面运行时由 Swift 直接提供文件。[官方部署文档](https://docusaurus.io/docs/deployment)

拟定构建顺序：Markdown 与元数据校验 → React 静态构建 → Pagefind 索引 → 链接与版本校验 → 拷贝到 app bundle → 桌面打包与签名。构建失败必须让发布失败，不能悄悄丢失文档资源。资源和索引在签名前写入 bundle，不在应用运行时修改签名资源。

构建配置需设置 `/developer/` 为 baseUrl，正文路由前缀与之协调，避免生成 `/developer/developer/`。建议生成带尾斜杠的目录型 HTML，桌面服务明确支持目录下的 index.html。

Swift 静态路由需要单独实现：

- 先匹配 `/developer/`，从文档 bundle 读取，不能落入 mobile-web 目录。
- 规范化 URL 解码后的路径，并检查目标仍在文档资源根目录，禁止路径穿越。
- 处理 `/developer` 到 `/developer/`、章节目录 index.html、正确的 HEAD 与 404。
- 历史深链接刷新直接返回对应页面；不要把不存在的章节一律返回首页。
- 支持搜索所需 MIME，尤其 Pagefind 的 wasm；现有 MIME 表尚无显式 wasm 项。
- HTML 和发布元数据用可更新缓存策略，带内容哈希的资源才使用长期缓存；搜索索引缓存必须与对应构建一致。
- 原有 PWA Service Worker 不应拦截 `/developer/`；验证同源下 scope 与导航回退行为，必要时调整 Mobile 的路径排除规则。

这些都是待实现工作。当前服务器虽然已经能返回插件静态资源，并不代表上述文档站行为已自动具备。

## 8. 分阶段实施

### 本阶段：调研与文档

交付 API 参考、认证与 SSE 接入示例、当前功能边界、框架比较、目录和托管方案、版本与搜索规则。文档站尚不创建 app/developer-docs 工程，不更新文档站依赖；通用 API 路由及调用来源单独实施。

### 下一阶段：文档工程

创建 React / Docusaurus 工程，拆分当前 Markdown，形成导航和主题；接入本地搜索、版本选择与历史页面。先验证静态构建和深链接，再冻结第一版文档。

### 后续阶段：桌面集成

增加 bundle 资源打包、`/developer/` 路由、独立文档开关和桌面入口，处理与 Mobile API 开关及 Service Worker 的关系。

### 发布阶段：兼容与历史

将文档版本冻结步骤纳入发布流程，接口变更同时更新正文，保证旧版本仍能查阅；随应用打包所有已发布文档和对应本地索引。

## 9. 验收标准

| 类别 | 验收 |
| --- | --- |
| API 完整性 | 文档路由、认证、字段和错误与核验提交对应，不宣称未实现能力 |
| 桌面启动 | 正式应用能打开文档，无需用户安装 Node 或启动开发服务器 |
| 独立性 | 插件更新/卸载不破坏文档；文档开关不意外开启已关闭的 Mobile API |
| 离线 | 断网可浏览正文、资源、历史版本和搜索结果 |
| 版本 | 可切换两个真实冻结版本；旧正文与导航不被当前编辑覆盖 |
| 搜索 | 中文、路径与字段可搜索；当前版本过滤和跨版本模式均准确 |
| 路由 | 历史章节直接打开、刷新、前进后退正常；未知路径 404 |
| 隔离 | 无真实 Token / 凭证进入静态文件或搜索索引，不自动调用 credentials |
| 兼容 | 本机、局域网与配置的 HTTPS 子路径下资源和搜索可用 |
| 发布 | 打包包含版本元数据；失败的文档构建阻止不完整发布 |

首版上线时只有一个真实冻结版本，可用 next 与首版先验证切换；第二次正式发布后再验收两个发布版本，不能为了演示制造虚假历史。

## 10. 通用 API 定位与后续可扩展项

内部仍使用 MobileSyncServer / MobileSyncManager 名称，公开路径统一为 /api/v1/，服务设置显示名称调整为开放 API 服务。这些是实现历史，不是未来用户应用的接入限制。后续可评估独立的开放 API 设置与服务生命周期、权限分级、稳定公共契约和路径迁移；旧 /mobile/ 路由不保留，旧版 Web Mobile 一律失效；历史文档保留查阅但必须显示失效标识。

新增能力以通用应用需求设计，不把 Mobile UI、Agent 池页面或单一插件包当成所有调用者的前提。文档需要同时提供浏览器与非浏览器的接入方式，明确部署、认证与连接管理差异。

OpenAPI / JSON Schema、请求调试器、自动提取 Swift payload 字段、多插件安装注册、连接 ID 驱动的供应商代理、细粒度只读 Token、任务操作 API 都可以后续设计。它们属于不同功能，不作为本次文档站首期的先决条件。

第一版重点是把现有真实契约讲清楚，并让文档能随桌面离线运行、随发布积累可查询历史。
