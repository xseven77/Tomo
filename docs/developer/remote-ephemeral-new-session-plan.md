# Owner-created ephemeral ChatGPT session

## Implementation evidence (2026-10-04)

The native owner settings now offer an explicit new-session action with a registered account, CLI executable and local workspace. A dedicated process calls `thread/start` once and requires the response to confirm an ephemeral, pathless thread at the selected cwd. An ambiguous or malformed response stops the process. The only idle `message.send` grant is tied to that freshly created process binding; existing resumed threads remain unable to start an idle turn. The new runtime is registered under its exact workspace, with a single-session directory and Tomo journal-backed history; detaching withdraws both registrations.

The installed CLI 0.153.4 rejects `thread/read includeTurns=true` for ephemeral threads (`-32600`). Its owner process does expose an empty idle `includeTurns=false` metadata read. Only before the first turn, the new-session path imports that validated empty baseline behind the event checkpoint. Normal resumed threads retain full-history hydration. The isolated two-process CLI probe and the real-CLI Swift empty-session integration test passed without a model turn. Synthetic stdio tests cover local creation, catalog/history, workspace registration, first ledger-backed start, reply event projection into journal-backed history, malformed acknowledgment, and old controlled-session regression.

Real model turn events, mobile authorization, history after process loss, long-history pagination, and actual-device UI remain unverified. This is progress toward the session loop, not completion of it.

The installed Codex CLI 0.153.4 provides `thread/start {ephemeral:true,cwd:<trusted local workspace>}`. This is an explicit *new* session path. It does not turn an existing idle thread into one owned by Tomo. Existing resumed threads retain the current restriction: `turn/start` is not offered because the CLI has no atomic idle precondition and may steer a turn running elsewhere.

`app/Tomo/Checks/verify-ephemeral-thread.py` starts two real app-server processes in the same isolated `CODEX_HOME`, with no user credential or model turn. The first creates a pathless ephemeral thread, then reads it. The second process cannot read or resume that ID. The thread creates no rollout file or `threads` row. App-server startup itself creates several SQLite databases; their existence is not evidence of materialized session history. The probe inspects the specific row.

Implementation contract:

1. Native owner chooses a locally registered account/runtime source and a canonical workspace. The workspace must be a directory approved on the desktop; the phone cannot supply a path, vendor ID, model, instructions or approval policy. Create a fresh private app-server and call `thread/start` once with `ephemeral:true` and the resolved workspace. Require an acknowledged UUID, `thread.ephemeral == true`, `thread.path == null`, exact returned cwd, and a quiet initial `thread/read` before publishing anything. Unknown or canceled outcomes stop that process. No retry of `thread/start` on an uncertain result.
2. Assign new opaque `runtimeId` and `sessionId`, scoped to that process. Hydrate the existing journal/event pump from the private `thread/read`; publish only the new source. Mark the pump binding as `exclusivelyCreated`, which is never set by resume/history paths. Only this binding may grant `permitsFreshStart`; keep the existing control-revision, pending-request and one-start-per-revision checks. Steer and interrupt continue to use the private current turn ID and exact CAS. Do not infer ownership from a shared `CODEX_HOME` or a lock file.
3. The directory adapter for this source must enumerate the single known session from Tomo's private owner registry and journal, not from CLI SQLite. Read current history from the same owner process/journal. All catalog/session/command routes retain server/agent/runtime/session ACL and the existing owner approval path. On process loss or stop, revoke commands immediately. Existing journal data can remain as historical read-only content; ephemeral CLI threads cannot be resumed after process exit, so show that lifecycle fact in the UI.
4. Surface “new session” as an explicit native desktop action. Remote clients may request a new session only if a separately implemented, bounded owner-approved operation grants it; do not reuse the local source choice as remote permission. On success use the regular session UI; on uncertain failure show an unknown outcome and require a new explicit owner action.

Required validation: synthetic stdio duplicate/unknown ack and cancellation races; installed CLI creation plus cross-process read/resume negative test; real private process with a model turn and events; lost reply, stop/restart and journal-only history; ACL denial and revocation; concurrent owner UI action; native session UI and exact account/workspace selection. No test with a synthetic rollout or empty ephemeral session proves the actual model loop.
